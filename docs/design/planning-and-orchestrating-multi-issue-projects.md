# Planning and orchestrating multi-issue projects

As-built design of https://github.com/dbaggott/claude-plugins/issues/223, accepted by the project review at https://github.com/dbaggott/claude-plugins/issues/223#issuecomment-6180293660.

Section IDs (`C#`, `R#`, `D#`, `Q#`, `A#`) are the ones the children, PRs and commits cite, unchanged from the tracking issue; a retired entry is marked retired, not deleted.

The unit the orchestrator works on is **an issue**. A plain issue is both the design and the unit of work: "orchestrate the resolution of issue 123" drives one author and one reviewer, integrates the two, and surfaces to the operator only what needs them. A tracking issue with sub-issues is the generalization: the same loop over each ready child, in dependency order, with the parent's body as the design. Everything in stages 1–3 exists to make that generalization work; stage 4 works without them.

The project built the process it is written in, staged (D10).

## Problem

Large projects today go: an agent-summary design doc in Obsidian → issues filed from it → each issue resolved by an author session and reviewed by a reviewer session, with the operator relaying questions between author, reviewer, and whichever session wrote the design. Four things go wrong, repeatedly:

- **The gaps between issues have no owner.** The design is outside GitHub, so no issue, reviewer, or resolver can read it. `issue-reviewer`'s set pass checks overlap, phasing, and orphaned work only against the other issue bodies; the plan is not an input, so "something the plan implies that no issue owns" is a guess.
- **Dependencies are prose.** An acceptance criterion that cannot run until another issue lands is invisible until someone tries to run it.
- **Mid-flight decisions reach chat, not the design.** `resolving.md` surfaces design changes to the operator before a PR leaves draft, which is the right gate, but the design never learns the answer and cascades onto sibling issues are found by the operator.
- **The operator is the message bus.** Every question is relayed by hand, and decisions that an orchestrator with the design in hand could make are instead made by whoever is at the keyboard.

## Goals

- A design is a first-class GitHub artifact that issues cite, reviewers judge against, and an orchestrator updates.
- Issues are decomposed from the design with traceability both ways, and dependencies are machine-readable.
- The set of issues is reviewed against the design before implementation starts, and findings can flow back into the design.
- An orchestrator runs implementation of one issue, or of a tracking issue's children: orders the work, dispatches author and reviewer agents, answers what the design answers, escalates what it does not, detects systemic problems, and survives its own restart.
- The process reports on itself: every dispatched agent leaves a retrospective, and patterns across them become upstream issues.
- The operator's attention is spent only at: design acceptance, escalations, and merges. The operator does not read or approve the children: the set review's `READY` on every child is that gate, and a child reaches the operator only through an escalation (D16).

## Non-goals

- Replacing the per-issue author/reviewer flow. It stays as is; the orchestrator drives it.
- Any forge other than GitHub. The issue flow is GitHub-only already.
- Letting any agent merge. Humans merge.
- A general project-management UI. GitHub's own sub-issue and dependency views are enough.

## Constraints

Verified facts the design rests on. Each was checked on 2026-10-13; the method is named so it can be re-run.

- **C1. Subagents have no `AskUserQuestion`.** Documented as stripped from every subagent, and confirmed by experiment: a `general-purpose` subagent could not find the tool directly or via `ToolSearch`. An ask site that calls it inside a subagent is a dead end.
- **C2. `SendMessage` resumes a finished subagent with full context.** Confirmed by experiment: a resumed subagent answered from memory and saw its own earlier steps. Docs state no limit on resume count or delay; transcripts are kept 30 days by default. A subagent stopped by hand refuses resumes.
- **C3. Plugin machinery is active inside subagents.** Confirmed by experiment: `check-issue-create.sh` fired on a subagent's `gh issue create --help`, the always-on rules arrived via `inject-rules-subagent.sh`, the Skill tool listed every `dnbg-*` skill, and the Agent tool was present (nesting depth limit is 3 per docs).
- **C4. GitHub sub-issues and blocked-by relationships are available** through REST (`/issues/{n}/sub_issues`, `/issues/{n}/dependencies/blocked_by`), GraphQL (`subIssues`, `parent`, `blockedBy`, `blocking`, summaries, and mutations), and `gh` 2.102.0 (`gh issue edit --parent/--add-sub-issue/--add-blocked-by/--add-blocking`; `gh issue list --json blockedBy,blocking,parent,subIssuesSummary`). Verified by live queries against this repo. Limits: 100 sub-issues per parent, eight levels deep, same repository owner required.
- **C5. Issue body edit history is full snapshots, not diffs.** GraphQL `userContentEdits` on an issue returns, per entry, `editedAt`, `editor`, and a field named `diff` that holds the complete body after that entry (verified: the newest entry equals the current body). The creation body is in the list: the oldest entry is stamped at `createdAt`, attributed to the issue author, and holds the body as filed (verified 2026-10-14 on the tracking issue, whose first entry still carries the duplicated heading the first edit removed; the resolver of child 2 found this by testing, correcting an earlier count-based inference that the creation body was not recorded). A never-edited issue has no entries, and its current body is the creation body. A diff must be computed locally from two snapshots.
- **C6. There is no API for issue attachments on GitHub.** Uploads go through a cookie-authenticated browser path only. Verified 2026-10-13 by web search: no REST or GraphQL endpoint in GitHub's docs, a GitHub community discussion with no working answer, and the `gh-attach` tool's own README stating it borrows browser session cookies. Attachments are not an option for storing anything.
- **C7. Subagent lifecycle limits.** Default 20 concurrent subagents; each has its own context window; background subagents survive a process restart via the supervisor; what `/clear` does to them and whether a subagent can be resumed from a different parent session are undocumented. Verified 2026-10-13 against the Claude Code docs pages for subagents, worktrees, agent view, and sessions at code.claude.com; re-check those pages when the client version moves, since the limits are the client's, not this design's.
- **C8. Issue body size is 65,536 codepoints.** Not in GitHub's docs; the figure is the API's own validation error ("Body is too long (maximum is 65536 characters)"), reported consistently across projects and in the community limits list at https://github.com/dead-claudia/github-limits. The tracking issue's body was about 30,000 characters after the first review round and reached about 59,000 by closeout, before the friction log was disposed, as the decision and friction logs grew, so the ceiling was a live constraint (Q6).
- **C9. Existing watch tooling covers issues.** `dnbg-workflow/scripts/watch-issue.sh` blocks until comment, linked-PR, or body-edit activity on a set of issues and reports which; `fetch-issue-state.sh` is its one-query source. Verified present at commit `9a4c0b7`. Its author and reviewer roles each exclude one login by exact match. The orchestrator arms no issue watch: its event source is a subagent ending its turn, and the operator's answers come in chat, or, in a headless run, as a comment on the parent that the next loop or a restart reads. Child 7 first gave it an issue watch under an `orchestrator` role that excluded no login, but every event that watch reported already reached the orchestrator as an agent's report or a chat answer, so each wake replayed the whole context for no action, and the role existed only to filter the orchestrator's own writes back out. The watch and the role were dropped by https://github.com/dbaggott/claude-plugins/issues/321; a revision that wants the orchestrator to see something should have the agent that sees it report it.
- **C10. A subagent shares its parent's `CLAUDE_CODE_SESSION_ID`.** Confirmed by experiment: a `general-purpose` subagent printed the same id as the main session. The own-claim test in `claiming.md` therefore passes for an author dispatched by the session that made the claim.
- **C11. A forge seam already exists.** `docs/forge-support.md` states that another forge needs its own backend behind a shared contract, and https://github.com/dbaggott/claude-plugins/issues/149 (open) is where that contract is defined. `fetch-issue-state.sh` is the pattern: forge-specific queries inside, one forge-neutral object out, with the GitHub assumption marked at a single point.

## Requirements

Grouped by stage. Each is meant to be checkable.

### Stage 1: design

- **R1.** A design is the body of a tracking issue in the project's repo, carrying in fixed sections: problem, goals, non-goals, constraints, requirements, decisions, open questions, end-to-end acceptance criteria, a decision log, and a friction log.
- **R2.** Constraints, requirements, decisions, open questions, and acceptance criteria carry stable IDs that are never renumbered. Retired entries stay, marked retired, so citations never dangle.
- **R3.** Every decision records its rationale and its reversal condition ("chose X because Y; revisit if Z"). A decision without a rationale is a review finding. A reversal condition may be stated as "none identified", which is an explicit answer and not an omission; the reviewer flags only its absence. The reason for the escape hatch: forcing a condition where none is known produces an invented one, which is worse than none because later readers trust it. Whether reversal conditions earn their keep was left to the friction log, which recorded no case against them.
- **R4.** Every open question carries a default. A question without a default is a review finding.
- **R5.** `issue-reviewer` has a design-review mode that judges a tracking-issue body against R1–R4 and additionally asks: is each requirement checkable, are the interfaces between parts named, do end-to-end acceptance criteria exist, and is every decision one the design author could actually make (not a disguised operator question).
- **R6.** A design is *accepted* when it holds a `READY` verdict from that mode and the operator's sign-off is recorded in the decision log. Acceptance is a log entry, not a merge. This design was accepted on 2026-10-14, before R5's mode existed (D10's staging): `READY` at plain spec review round 3 (https://github.com/dbaggott/claude-plugins/issues/223#issuecomment-6158017875) and the operator's sign-off in session. The design-mode `READY` followed once child 3 shipped the mode (https://github.com/dbaggott/claude-plugins/issues/223#issuecomment-6159052434).

### Stage 2: decomposition

- **R7.** Child issues are GitHub sub-issues of the tracking issue. Each child body has a fixed "Covers" section listing the requirement IDs it satisfies, including every cross-cutting requirement it touches (R28 whenever the child adds a forge call), and names the parent's relevant sections as required reading.
- **R8.** Dependencies between children are GitHub blocked-by relationships. The relationship is the source of truth; a "Depends on" line in the body is a human-readable mirror, and a mismatch between the two is a review finding.
- **R9.** Every child acceptance criterion is runnable at that child's merge, per `creating.md`'s existing rule. Anything no single child can run is an end-to-end criterion on the parent, and the parent says which children contribute to it.
- **R10.** Decomposition is a documented procedure a session can follow cold from an accepted design: which sections become which children, how to assign IDs, how to set relationships. Where it lives (a skill, or a section of `issue-workflow`) is Q1.

### Stage 3: set review

- **R11.** `issue-reviewer`, given a tracking issue, reviews the parent plus all of its sub-issues as one set, snapshotted in one query, and reports in addition to its existing overlap, phasing, and orphan checks:
  - **coverage**: every requirement maps to at least one child, or is explicitly marked end-to-end or deferred in the parent;
  - **unrealized dependency**: a child criterion that needs another child's output with no blocked-by relationship between them;
  - **drift**: a child whose approach contradicts the design section it cites.
- **R12.** A set-level finding that the *design* should change attaches to the parent, and the author's response is a parent body edit plus a decision-log entry, not a child edit.

### Stage 4: orchestration

- **R13. Delegated mode.** An *ask site* is any instruction whose next step needs an operator answer: an `AskUserQuestion` call, or prose that tells the agent to ask, stop and ask, get buy-in, or surface something before proceeding. Every ask site in every `dnbg-*` plugin's skills and always-on rules has a branch for the case where `AskUserQuestion` is absent (C1). The branch does two things in order: post the question as a comment opening with the fixed line `Delegated question:` on the issue being worked (on the PR when there is no issue, as with `git-workflow`'s pickers on issue-less work), then end the turn with the question as the report. Where there is neither an issue nor a PR, as at `dnbg-work-summary`'s recap-axes picker, the branch takes the defaults the site already recommends, states them in the report, and ends the turn; a site with no recommended default ends the turn with the question as the report and nothing else. It never picks silently. The check has two parts. First, the grep, case-insensitive, read hit by hit rather than counted: `grep -rn -i -E "AskUserQuestion|ask the operator|stop and ask|ask with|get buy-in|surface .* before|unattended|surface it to|ask which|instead of proceeding|, ask;|stop and surface|before filing any|tell the operator which" dnbg-*/skills dnbg-workflow/always-on-rules.md`. Second, every site this requirement names must appear in the grep's hits, so a pattern that drops a known site fails visibly; a site found outside the pattern is added both to the pattern and to the list here, by the finding session before orchestration starts and by the orchestrator once it has (D4); a child that finds one under orchestration reports it as a `Delegated question:` and the orchestrator makes the edit. `dnbg-work-summary` and `dnbg-practices` are in scope; `dnbg-workflow` is where the first pass and the eval (R25) concentrate. Sites known at commit `9a4c0b7` that the grep finds beyond the `AskUserQuestion` calls include `resolving.md` lines 46, 87, 96, and 130, `reviewer/SKILL.md` lines 105 and 111, `issue-reviewer/SKILL.md` line 31, and `dnbg-work-summary/skills/work-summary/SKILL.md` line 233; outside the original pattern, and added to it by child 4, `resolving.md` line 83 ("instead of proceeding"), `reviewer/SKILL.md` line 78, `dnbg-work-summary/skills/work-summary/SKILL.md` line 51 ("ask which"), and that file's line 82 (", ask;"); and, in files landed after `9a4c0b7`, `issue-workflow/references/decomposing.md`'s parent-conflict stop ("stop and surface") and `orchestrate/references/closeout.md` line 38 ("tell the operator which") and lines 46 to 49 ("before filing any"). The `AskUserQuestion` calls at that commit: `git-workflow/SKILL.md` lines 55 and 151 (send-to-review picker), `git-workflow/references/review-rounds.md` line 106 (findings picker), `reviewer/SKILL.md` lines 58 and 92, `issue-reviewer/SKILL.md` line 28, and `issue-workflow/references/resolving.md` lines 109, 118, and 122 (critical-review concern, design buy-in, unattended stop). The list is illustrative; the requirement is every site. As built, no test runs the grep; the line numbers are those at the time each site was found, and the list records the sites known when the project closed rather than a maintained registry.
- **R14.** The delegated trigger is mechanical (the tool is absent), never inferred from operator phrasing. The existing "unattended" wording in the skills is reconciled with it (Q2).
- **R15. The orchestrate skill.** Given an issue URL, a main-session agent first claims it (R21), then:
  - **Single-issue mode** (the issue has no sub-issues): dispatch one author subagent to resolve it (pre-answered to send to review and auto-handle rounds) and one reviewer subagent (reviewer issue mode on it); wait for each subagent to end its turn, whose report is the event (C9), never by polling in-conversation; handle each event per R16–R18; stop when the PR merges and the issue closes, or when stopped. The issue's own body is the design for triage purposes.
  - **Multi-issue mode** (the issue has sub-issues): loop until every sub-issue is closed or it is stopped: compute the ready set (open sub-issues whose every blocker is closed *as completed*, since a blocker closed as not planned or duplicate never delivered what it stood for; no assignee; no `assigned:*` label; a `READY` spec verdict where the project uses spec review, and the parent's own latest verdict `READY` too, else no child is ready; the verdict's first line is a stated contract in `issue-reviewer`, which `ready-set.sh` parses); claim each child it is about to dispatch (R21); run single-issue mode on it, up to a concurrency cap (Q3); handle events; repeat. When every child is closed, author the closeout PR (R22) and stop when it merges; the orchestrator never judges the end-to-end criteria itself. The parent's body is the design.
- **R16. Triage.** The design, for triage, is the parent body in multi-issue mode and the issue's own "Proposed approach", rejected alternatives, and acceptance criteria in single-issue mode. The orchestrator answers a question when the design's recorded rationale covers it, continuing the asking agent via `SendMessage` (C2) and recording the answer on the issue. It escalates to the operator anything that changes an external contract or user-visible behavior, changes scope, chooses between competing values, or contradicts the design. An escalation holds up only the asking child when the orchestrator runs headless, since the question is posted and the other agents keep running; in an interactive session `AskUserQuestion` pauses the whole loop until answered, a cost of D7 to accept rather than a defect. Escalation policy is escalate-by-default with an explicit allowlist of what it may decide (D11).
- **R17. Logging.** Every answer, every escalation outcome, and every *application of a prior decision to a new case* is a row in the decision log naming the decision ID, the child, and the state (`proposed`, `decided`, `applied`). In single-issue mode the log is the issue's comments, with decisions promoted into the body per `issue-workflow`'s maintenance rule. Silent application of a prior decision is the failure this exists to prevent.
- **R18. Design changes during execution.** On a `decided` entry: the orchestrator edits the parent's design section at once, sweeps every child whose "Covers" or body cites the affected IDs, updates those bodies, re-runs the spec review on the ones that changed materially (Q4), pings any running agent on an affected child via `SendMessage`, and marks the entry `applied` only once every re-reviewed child reads `READY` again, dispatching none of them before that, since a child under re-review still carries its old verdict. Every `decided` entry, including a plain answer to one child's question, finishes through this path and ends `applied`; a decision raised on the parent reaches a child as a promotion into the child's body that links the parent row, with no `Decision log:` comment on the child. A restarted orchestrator finishing a `decided` entry it did not start is the normal path, not an edge case.
- **R19. Systemic detection.** The orchestrator raises a design-level finding, logged and escalated, when: two or more questions from different children touch the same requirement or decision; a reviewer finding recurs across children's PRs, where the same finding means the reviewer cites the same R or D ID, or the same file and finding category, and recurrence means its second appearance on a different child's PR; or one prior decision has been applied more than N times (Q5).
- **R20. Statelessness.** The orchestrator holds no state that is not in GitHub. Killing it at any point and starting a fresh one with the tracking issue URL resumes correctly. It is the main session, not a subagent (D7); its authors and reviewers are fresh subagents each dispatch, never resumed across orchestrator restarts (C7). The reviewer still withholds claim marks, as `issue-mode.md` requires.
- **R21. Claims and boundaries.** The orchestrator claims the issue it orchestrates with the standard three marks from `claiming.md` (assignee, `assigned:*` label, claim comment carrying its session id), so a second orchestrator pointed at the same issue sees a foreign claim and stops. Before dispatching an author to a child, the orchestrator puts the same three marks on the child, so the ready set excludes it before any author exists; the author then passes the own-claim test by C10 and does not claim again. Within one orchestrator every agent carries the same session id, so the claim test cannot tell siblings apart, and nothing may depend on it doing so: the pre-dispatch claim is the only guard against double dispatch. On restart the new orchestrator has a new session id: it surfaces the predecessor's claim to the operator, and on confirmation re-claims the tracking issue and every in-flight child (Q9). The orchestrator never merges. Design-section body writes during execution are the orchestrator's alone (D4).
- **R22. Whole-project acceptance and closeout.** The tracking issue resolves the way a plain issue does. When every child is closed, the orchestrator authors one closeout PR, carrying `Closes <parent URL>`, that writes the as-built design into the repo (`docs/design/<slug>.md` or the repo's own convention) and gives every friction-log entry a disposition: a follow-up issue or an explicit drop. `reviewer`'s issue mode, pointed at the tracking issue, reviews that PR, grading the union of merged child PRs and the doc against the parent's end-to-end criteria in one review, and the project closes when the operator merges it. Every end-to-end criterion met by a run that no child's own criteria record is run by the orchestrator and recorded in the PR's description; a criterion with no recorded run is a finding on the PR, answered in the next round. Because: a verdict on the parent ahead of its closeout reviewed the project before the work that finishes it, could not grade the closeout itself, and turned its fixes into comment rounds on an issue; the first project review on this design blocked on A6 and A7, runs nobody had recorded. Revised by https://github.com/dbaggott/claude-plugins/issues/287.
- **R23. Closeout.** *(retired: folded into R22 by https://github.com/dbaggott/claude-plugins/issues/287)*

### Tooling and evaluation

- **R24. Issue-diff script.** `dnbg-workflow/scripts/issue-diff.sh <owner/repo> <n> --since=<iso> [--until=<iso>]`, in `fetch-issue-state.sh`'s argument and result-line shape, prints a unified diff of the body between the two nearest snapshots (C5), prefixed with each snapshot's `editedAt` and editor. Consumers: `issue-reviewer` rounds (`--since` the `lastEditedAt` it reviewed against), an orchestrator on restart (what changed in the parent since its last log row), and the operator. As built, the script fails with `result=ERROR reason=issue-query-shape` on an issue with a long edit history, which is the heavily edited tracking issue these consumers read; https://github.com/dbaggott/claude-plugins/issues/268 owns the fix.
- **R25. Delegated-mode eval.** A reproducible test: a child issue with a planted ambiguity that has no default, resolved by a subagent author, passes when the ambiguity surfaces as a comment opening with `Delegated question:` plus a report, rather than a silent choice or an unmarked comment. Runs N times (default 5) and reports the count. The baseline on the pre-R13 skills found that `resolving.md`'s existing unattended branch already comments and stops at the critical-review site, so the prefix is what separates before from after; a second fixture at a site with no unattended branch (the send-to-review picker, stopping with the prefix on the PR) is child 4's to add.
- **R26. Restart eval.** A reproducible test: kill the orchestrator between a `decided` entry and its sweep, start a fresh one, and pass when the sweep completes and the entry reads `applied`.
- **R27. Set-review eval.** A deliberately incomplete decomposition (one uncovered requirement, one undeclared dependency) is reviewed and both are reported.

### Forge seams

- **R28. Cross-cutting.** Every new forge call this project adds (sub-issue and dependency queries, the ready set, body snapshots, claims) lives in a script that prints a forge-neutral object, following `fetch-issue-state.sh` (C11); skills consume only the neutral shape and never call `gh api` for these directly. The GitHub assumption is marked once per script, in the form issue 149 expects. Nothing here implements another forge; the requirement is that adding one later touches scripts, not skills. Every child that adds a forge call lists R28 in its Covers line (R7), so the set review's coverage check cannot read R28 as satisfied by one child. As built, no single script owns the sub-issue walk: `fetch-issue-set.sh` snapshots a parent, its sub-issues and their blocked-by edges for the set review and closeout; `ready-set.sh` runs its own walk, since the ready set needs blocker state, assignees, labels and comments that the snapshot does not carry; and `pr-sources.sh` finds the PRs linked to an issue. Each prints a forge-neutral result, so R28 holds, but a second forge implements the walk in two places.

### Process feedback

- **R29. Retrospectives.** At the end of every dispatch, the orchestrator continues the finished agent (C2) with a fixed retrospective prompt: what slowed or blocked you; what a skill told you that was wrong, missing, or contradicted by the tree; what you worked around; what you wished you could have asked. The agent writes the answer as a local file with frontmatter (tags, role, issue URL, skill versions) under a configurable directory, a `userConfig` knob defaulting to `~/.claude/dnbg-retrospectives/<owner>/<repo>/`; an operator who keeps such files elsewhere sets the knob. The orchestrator, as the parent's only writer (D4), folds project-level items into the parent's friction log. A dispatch interrupted by an orchestrator restart leaves no retrospective, since D6 forbids resuming it; that loss is accepted.
- **R30. Process review.** A documented procedure, runnable by a fresh session, reads a batch of retrospectives, reports patterns with counts and examples, and proposes upstream issues per the always-on "when shipped tooling doesn't fit" rule, filed only with the operator's approval of the exact text.

## Decisions

- **D1. The design lives in the tracking issue body, during planning and execution; the repo gets an as-built copy at closeout (R22).** Because: no merge gate on design iteration, one artifact for design and execution state, `issue-reviewer` already reviews bodies as specs in rounds, and it matches "the body is current truth." Revisit if: a real design hits the body size limit (C8); an agent rewrites intent without a log entry and the editor audit (C5) fails to catch it; or snapshot-based review proves inadequate even with R24.
- **D2. GitHub sub-issue and blocked-by relationships are the dependency source of truth (R8).** Because: C4, and `gh issue list --json` makes the ready set one call. Revisit if: a project spans repository owners, or the plugin adds a second forge.
- **D3. The decision is the gate; recording is not.** The orchestrator acts on a `decided` entry at once and the body edit is part of applying it, not a precondition. Because: with the design in an issue there is nothing to merge, so waiting buys nothing. Revisit if: acting before the body update produces log-versus-design drift that the sweep misses.
- **D4. During execution only the orchestrator writes the parent body; the operator decides through in-session answers or comments.** Because: body edits are whole-body replaces and two writers clobber each other. A child orchestrator that does not orchestrate the parent is not its writer: it posts project-level items, such as its retrospective's, as a comment on the parent, and the writer folds them; a multi-issue orchestrator folds directly. Revisit if: operator edits are frequent enough that the relay is itself friction, then design a lock protocol instead; or a project runs children under a multi-issue orchestrator while a separate design session also writes the body, which this decision forbids. The shipped `orchestrate/references/retrospective.md` still tells a child orchestrator to edit the parent's friction log; https://github.com/dbaggott/claude-plugins/issues/272 brings it in line with this decision.
- **D5. Delegated mode triggers on tool absence, not operator phrasing (R14).** Because: today's "unattended" is undetectable and every ask site is a dead end in a subagent (C1). Revisit if: Claude Code gives subagents an ask channel to the operator.
- **D6. Authors and reviewers are fresh subagents per dispatch, continued via `SendMessage` for answers within one orchestrator lifetime, and never resumed across orchestrator restarts.** Because: C2 makes continuation cheap and correct; C7 leaves cross-session resume undocumented; a fresh author finds the existing branch and PR through `git-workflow`'s open-PR check. Revisit if: cross-session resume becomes documented, or the 20-subagent cap binds.
- **D7. The orchestrator is the main session, not a subagent.** Because: only the main session can ask the operator anything (C1). Revisit if: C1 changes.
- **D8. The orchestrator is never the design author; it must work cold from the body.** Because: it is the test that the body carries the design, the same discipline issues are held to, and a fresh agent has no stake in old decisions. Revisit if: dogfooding shows cold orchestrators misreading intent in ways the log could not have carried.
- **D9. Decisions are positions, not contracts.** A discovery the design's author could not have known is a new decision by definition, not a lookup. "The design answers this" means the recorded rationale covers the case, not that the text mentions it. Because: this is the stated failure mode of design documents becoming gospel. Revisit if: the rule produces so many escalations that the orchestrator decides nothing (then narrow it with evidence from the log).
- **D10. This project runs under its own process, staged.** Hand-orchestration until the orchestrate skill lands; children ordered so it lands with work remaining. A friction log separate from the decision log records where the process, not the project, hurt. Because: the alternative is writing four skills from imagination. As built, the staircase's last step was not taken: children 11 and 12 ran as two single-issue orchestrators in parallel sessions, by the operator's call, not under one multi-issue orchestrator on the tracking issue. Multi-issue mode's live evidence is child 9's testbed run (https://github.com/dbaggott/dnbg-watch-testbed/issues/52), which A1 names. Revisit if: the staging itself masks process problems the friction log cannot separate; or a multi-issue path turns up that only a run on a real project would have exercised (the project review found none).
- **D11. Escalation policy starts conservative**: escalate by default, with an explicit allowlist of what the orchestrator may decide alone. The allowlist, as of this round: (a) applying a decision whose recorded rationale names the case at hand; (b) choosing among options the design already ranks, or taking the default of an open question; (c) implementation choices inside one child that change no interface, contract, user-visible behavior, or acceptance criterion; (d) ordering and scheduling of children within the dependency graph; (e) answering questions of fact about the tree or the forge state. Anything not on the list escalates, and additions to the list are decisions logged under R17. Because: too eager reproduces today's cost, too lax reproduces silent drift, and only the first is recoverable. Revisit if: after the first dogfood project the log shows escalation volume is the dominant friction.
- **D12. Humans merge everything.** Because: repo-wide principle of the plugin, and with D1 the only design PR is the closeout one. Revisit if: never, within this project.
- **D13. Single-issue orchestration is the base case; multi-issue is the generalization.** Because: the win the operator wants most is one agent driving author and reviewer on one issue, and it needs none of stages 1–3; building it first also gives the project its own orchestrator earliest. Revisit if: the two modes diverge enough that one skill carrying both is harder to read than two.
- **D14. Forge-specific calls go in scripts, not skills (R28).** Because: C11 is the established seam and the plugin's stated plan for other forges. Revisit if: issue 149 defines a contract the scripts here do not fit, in which case they move to it.
- **D15. The orchestrator claims what it orchestrates (R21).** Because: the standard claim already excludes a second orchestrator and, by C10, already admits the orchestrator's own authors, so no new marker is needed. Revisit if: the subagent session id stops matching the parent's, or two orchestrators need to share a tracking issue by design.
- **D16. The operator approves the design, not the children.** Decomposition and the set review converge between the decomposing session and the reviewer bot; the operator sees a child only through an escalation, and the gate before orchestration is every child `READY`. Because: reading twelve child issues is the attention cost this project exists to remove, and the set review is the check that a human read would have been. Revisit if: a project ships a child that the set review passed and the operator would have caught on a read, in which case the fix is a set-review finding, and only if that fails, a gate.
- **D17. The delegated-mode trigger lives at the ask sites, with one shared reference, not in the always-on rules.** Because: the instruction is needed only where a loaded skill asks, so a branch at the site is read at the moment it matters; always-on cost is paid by every session of every user; and an always-on paragraph would assume an issue is in context when many sessions have none. Revisit if: an ask turns up outside any skill, or child 4's eval shows agents not following a one-line pointer.

## Open questions

Each is settled, by a decision or by the default that was built.

- **Q1. Where does the decomposition procedure live?** Default: a `references/decomposing.md` under `issue-workflow`, since filing children is issue creation and the hook already routes there. Built: `dnbg-workflow/skills/issue-workflow/references/decomposing.md`.
- **Q2. How is "unattended" reconciled with delegated mode?** Default: delegated mode replaces it. The operator-stated "I'll be afk" case becomes pre-answered pickers, which already exist, plus the comment-and-stop behavior at sites with no pre-answer. Built: `issue-workflow/references/delegated.md`, and no "unattended" wording remains in the skills.
- **Q3. Concurrency cap for the orchestrator.** Default: three children in flight (six subagents). Built: `orchestrate/references/multi-issue.md` dispatches while fewer than three are in flight, or the cap the operator names.
- **Q4. After a design change, which children get re-reviewed?** Default: only those whose acceptance criteria changed, or whose body changed in a section their Covers line cites, as a subset run of `issue-reviewer`, not the whole set. Built: `orchestrate/references/design-change.md`, step 4.
- **Q5. Systemic threshold N for repeated application of one decision (R19).** Default: 3. Built: `multi-issue.md` raises the finding when one decision is `applied` more than three times, or past the parent's own Q5 threshold if it sets one.
- **Q6. Where do decision-log rows and friction entries go as volume grows?** Default: the body holds decision-log rows for the current phase and friction entries not yet disposed; when the body approaches 50,000 characters, the parent's writer moves completed-phase rows, and friction entries already disposed to a filed issue, into one comment each and leaves a pointer behind, so the body stays under C8 with headroom for a design change. Applied 2026-10-14 for both, through archive comments on the tracking issue; the body stayed under C8.
- **Q7. What if a design exceeds the body limit (C8)?** Default: split by design area into sub-issues that each carry their own IDs, with the parent holding goals, decisions, logs, and the area index. Not needed: no design here approached the limit.
- **Q8. Where does the delegated-mode trigger text live?** Decided 2026-10-14 (D17): one shared reference file, `issue-workflow/references/delegated.md`, plus a one-line branch at each ask site pointing to it; no always-on change. The earlier default (a paragraph in `always-on-rules.md`) is retired.
- **Q9. Does a restarted orchestrator re-claim automatically?** Default: no. It surfaces the predecessor's claim and its last activity timestamp and asks once; the operator confirms the predecessor is gone. An automatic rule keyed on staleness can come later with evidence. Built: `orchestrate/SKILL.md` asks once on a `FOREIGN` claim, and a headless run takes the answer from its prompt.
- **Q10. Which model does each dispatched role run on?** The Agent tool accepts a per-spawn `model` override (sonnet, opus, haiku, fable) and agent definitions can pin one; with neither, a subagent inherits the orchestrator's model. Default: inherit for every role until retrospectives (R29) show a role where a cheaper model would have done, then pin that role. Forks are excluded; they always run the parent's model. Built: the dispatch recipes name no model, so every role inherits; no role has been pinned.
