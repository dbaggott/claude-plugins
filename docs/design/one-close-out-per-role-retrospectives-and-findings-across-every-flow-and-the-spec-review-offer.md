# One close-out per role, retrospectives and findings across every flow, and the spec-review offer

As-built design of https://github.com/dbaggott/claude-plugins/issues/465.

Section IDs (`C#`, `R#`, `D#`, `Q#`, `A#`) are the ones the children, PRs and commits cite, unchanged from the tracking issue. Problem and Constraints describe the plugins as they stood before this work, verified at `14a6911`, and "today" in them means then.

Every flow in `dnbg-workflow` now ends the same way: each role closes out its part with a report, findings entries, and a retrospective, at a moment that lets the operator act before the merge, under one configurable policy for where process friction goes. Filing a plain issue ends with the offer of a spec review.

## Problem

Four flows get work done: working directly with an author agent on a PR; resolving an existing issue with an author agent and a reviewer, either as a subagent or in a separate session; orchestrating one issue; orchestrating a tracking issue. Two feedback systems sit beside them: retrospectives (process friction, read by `process-review`) and findings entries (what was found about the code, read by `findings-review` and a tracking issue's closeout). They diverge across the flows, and the divergence has one root cause: the two artifacts fire on different triggers.

- **Findings entries fire on a role event**, writing a Summary / Observations / Actionable report. That report exists in every flow (`git-workflow/references/merge.md`, "The report that goes with the command"; `reviewer/references/watch.md`, "Report the review, in three sections"; `orchestrate/SKILL.md`, "Stop"), so findings are already flow-independent.
- **Retrospectives fire on a dispatch event**, being the `author-orchestrated` or `reviewer-orchestrated` agent. The instruction lives only in `dnbg-workflow/agents/author-orchestrated.md`, `dnbg-workflow/agents/reviewer-orchestrated.md` and `orchestrate/references/retrospective.md`. No role skill mentions writing one (C1).

Evidence: every one of the 191 retrospectives under the operator's `~/.claude/dnbg-retrospectives/dbaggott/claude-plugins/` (counted 2026-10-28) was written by a dispatch of an `*-orchestrated` agent, whether `orchestrate` or `issue-workflow`'s spec-review spawn dispatched it. The direct-author and separate-reviewer flows, which carry a large share of the work, have produced none. This is an accident of history: the design's R29 (https://github.com/dbaggott/claude-plugins/issues/223) had the orchestrator deliver the prompt by `SendMessage`, https://github.com/dbaggott/claude-plugins/issues/328 moved it into the agent prompts, and the trigger stayed "I was dispatched".

The further inconsistencies this project resolves:

1. **Standalone friction has a competing outlet.** The always-on rule "When shipped tooling doesn't fit, tell the user" (`dnbg-workflow/always-on-rules.md`) sends friction to chat and an immediate upstream issue. Orchestrated friction goes to a file and waits for `process-review`'s count-of-two threshold. Same event, two policies, and the batch system never sees the immediately-filed ones except through its "search for an existing issue first" step.
2. **The spec reviewer's retrospective depends on who started it.** A `review <URL> as a spec` session writes none. The same skill spawned by `issue-workflow/references/spec-review-rounds.md`'s handoff, or by `orchestrate/references/design-change.md`'s re-review, writes one, because the spawn uses `reviewer-orchestrated`. The spec author's side never writes one.
3. **Reviewer observations reach the operator after the merge.** `merge.md` places the author's report before the merge so an item "can still send the PR back". The reviewer's report fires at `CLOSED`, after it. The operator merges and then learns something they would have added to the PR.
4. **Finding ownership requires the reviewer to infer the author's flow.** `findings-review/references/entry.md`, "Which items get an entry", has the reviewer skip findings the author didn't take "when the author follows `git-workflow`", and write them otherwise. On this machine 1 of 37 entries is reviewer-written; the text cannot say whether that is the rule working or reviewer-owned items being lost.
5. **The retrospective format lives with one producer, the findings format with its consumer.** `entry.md` sits under `findings-review`; `retrospective.md` sits under `orchestrate`, and `process-review` reaches into `orchestrate` for its own input format. `process-review`'s description and `docs/configuration.md` both describe retrospectives as something "`orchestrate`'s agents" write.
6. **The three-heading report is defined twice in full and once by reference** (C4), and the three copies have already drifted in which items qualify.
7. **A plain issue is filed and nobody is offered a spec review.** `issue-workflow/references/creating.md` hands a *tracking* issue to its reviewer (the "Tracking issue" option under "Is this one issue or a project?") and `references/decomposing.md` step 6 hands a *set* to review. "File it" for a plain issue ends with the `gh issue create` command and nothing after it (C5). An issue filed outside a project gets a spec review only if the operator thinks to ask.
8. **The missing-retrospective fallback exists only in `orchestrate`.** `retrospective.md`, "Asking the agents for one", nudges a dispatched agent with `SendMessage`; `spec-review-rounds.md`'s spawn only passes along whatever path the report names.
9. **One `role:` value covers two reviewers.** A spec reviewer and a PR reviewer both write `role: reviewer`, so `process-review`'s role spread mixes two skills.

## Goals

- Every role, in every flow, closes out its part the same way, defined once in that role's skill and independent of who dispatched it.
- What can still change the PR reaches the operator before the merge; what can only change the plugin is written after it.
- Process friction has one policy, set by the operator: kept for the maintainer in retrospectives, or surfaced to the user by severity, never both and never neither.
- Filing any issue ends with the offer of a spec review, and accepting it costs the operator one picker.
- Existing retrospectives and findings entries stay readable by `process-review` and `findings-review` without migration.

## Non-goals

- Changing the retrospective prompt's four questions, or the findings entry's fields beyond `role:` (D7).
- Making the stores anything other than local files. A reviewer run on another machine still leaves nothing a closeout here can fold; that is a known limit, stated rather than fixed.
- Spec-reviewing issues filed by `process-review` against *other* projects (upstream reports). Those are filed with the user's own `gh issue create` under the always-on rule, outside this plugin's review loop. As built, `issue-workflow/references/filing.md`'s "Reporting a gap upstream" gets no spec-review offer (https://github.com/dbaggott/claude-plugins/issues/471#issuecomment-6458276178).
- Any forge other than GitHub. The seam still has to hold: R17 says what each child owes it, so adding a forge later touches scripts, not the close-outs this project writes.

## Requirements

### Stage A: the shared report and the role close-out

- **R1.** The three-heading report (Summary, Observations, Actionable), the narrow-Actionable rule, the findings-entry hook and the retrospective pointer are defined in one reference file, and every site that produces the report cites it instead of carrying its own copy: `git-workflow/references/merge.md`, `git-workflow/references/post-merge.md`, `reviewer/references/watch.md`, `orchestrate/SKILL.md` "Stop", and the two spec-review close-outs R4 adds. Where it lives is Q1, settled at its default: `findings-review/references/report.md`. The orchestrator's Stop report takes the same retrospective pointer as every other site, so its own retrospective goes in the report's Retrospective section and Observations lists only the agents' (https://github.com/dbaggott/claude-plugins/issues/472#issuecomment-6458660908).
- **R2.** Each role skill carries its own close-out at the role's natural end, naming the moment: `git-workflow` at the post-merge cleanup or when the PR closes unmerged; `reviewer` at `CLOSED`, or at the end of an issue-mode assignment; `orchestrate` at Stop. The close-out is: the report per R1 (as a delta where a handoff already carried one, per R9), findings entries for the items `entry.md` names, and a retrospective per the retrospective reference (R7), which from R6 on carries the policy that says whether the file is written.
- **R3.** `dnbg-workflow/agents/author-orchestrated.md` and `dnbg-workflow/agents/reviewer-orchestrated.md` carry no retrospective instruction. Everything else they carry today stays: delegated mode, the cache TTL, pushing early, continuing a predecessor's PR, the operator check as a background task, the rule against `pkill -f` that `tests/coupling.bats` requires of both, the sibling-sweep note, how each turn ends and which turn carries the report. The test is what each line says: true of a dispatched agent and false of a standalone session doing the same role's work stays; a role instruction goes to the role skill.
- **R4.** The spec review has the same close-out on both sides: `issue-reviewer/references/rounds.md` at convergence or halt, and `issue-workflow/references/spec-review-rounds.md` at "Where it ends". Both write a retrospective per the retrospective reference (R7); neither writes findings entries (https://github.com/dbaggott/claude-plugins/issues/442, Q2's reasoning: a spec round's observations are settled in the round).
- **R5.** The nudge for a dispatched agent whose report names no retrospective path applies to every dispatcher: `orchestrate` and `spec-review-rounds.md`'s spawn. It lives once, in the retrospective reference (R7), and both cite it.

### Stage B: the retrospectives policy

- **R6.** A `retrospectives` configuration key, `on` or `off`, default `off` (D2). With it **on**, every close-out writes the retrospective file and says nothing about process friction in chat beyond the file's path in the report; the always-on rule's offer to file upstream applies only to friction that stopped the task from finishing. With it **off**, no retrospective file is written, and the close-out surfaces in the report only friction in the severe classes D3 defines, each as one line, followed by the always-on rule's offer to file upstream with the operator's approval of the exact text. The two-state rule is written once, in the retrospective reference (R7), per D5; each close-out cites it and carries no copy. The off state also turns off R5's nudge, since there is no file to ask for. The session note (C3) names the key when it is on, and the skills state `off` literally. In `docs/configuration.md` the key joins `version_stamp`'s kind, a key governing what a session publishes or says rather than a mechanical path or name, and C2's test literal gains it.
- **R7.** The retrospective format moves to `process-review/references/retrospective.md`, keeping the four headings, the frontmatter and the file-naming rule unchanged (D7). The fold-into-the-parent section stays under `orchestrate`, since it is orchestrator-only. `process-review`'s description, `docs/configuration.md`'s `retrospective_dir` row and `README.md` stop describing retrospectives as `orchestrate`'s.
- **R8.** The `role:` field of a retrospective takes `issue-reviewer` for a spec round and `reviewer` for a PR review; the file-name pattern is unchanged and `<role>` gains that one value. `process-review` reads both, and any older file's `reviewer` stays valid. `entry.md` is untouched: a spec review writes no findings entry (R4), so its `role` enumeration has no new value to carry.

### Stage C: timing

- **R9.** Each role has two moments. The **handoff**, before the merge, carries the full report per R1 and writes the findings entries for its items. The **close-out**, after the merge or the close, carries a delta report against the handoff and the retrospective. For the author this is `merge.md` then `post-merge.md`, already in that shape. For the reviewer the handoff is its `APPROVE` turn: it re-arms its PR watch, as the author does at its handoff, then ends that turn with the report in chat, so a separate-session reviewer surfaces its observations while the operator can still act, and `watch.md`'s `CLOSED` report becomes the delta. The delta takes `post-merge.md`'s existing form: only what arrived after the baseline, and "nothing new since the handoff" where a heading has nothing. The two reports are told apart by a fixed first line: the handoff opens `**Reviewer handoff: APPROVED at <sha>**`, and the end report opens `**Reviewer close-out: <merged | closed unmerged>**`; the author's two keep the shapes `merge.md` and `post-merge.md` gave them before. `report.md`'s opening list of report moments names the reviewer's handoff at its approval as well as its close-out (https://github.com/dbaggott/claude-plugins/issues/474#issuecomment-6458895879).
- **R10.** `orchestrate/SKILL.md`'s "Wait on subagent reports" gains the reviewer's handoff as an event of its own, recognised by R9's first line and held for the relay, so that only a report opening with the close-out line counts as the reviewer's end for "Stop". "Relay the merge handoff" then relays the reviewer's handoff report with the author's when it has arrived, and says it has not when it has not. Neither report holds the merge command.
- **R11.** The reviewer writes a findings entry for every finding it raised that stands unaddressed at its handoff, and the author writes one for every finding it declined; `entry.md`'s "One item has one writer" rule for the reviewer is replaced by that, and `findings-review` step 3 and `closeout.md` step 5 merge what lands twice (D6).

### Stage D: the spec-review prompt

- **R12.** Filing a plain issue from `issue-workflow/references/creating.md` ends with one `AskUserQuestion`: **"Spec-review it now (Recommended)"**, which dispatches `issue-reviewer` as `reviewer-orchestrated` on the issue and answers its rounds per `spec-review-rounds.md` with this session as the author; and **"Not now"**, which ends with the prompt to paste later (`review <URL> as a spec`). The first option takes `spec-review-rounds.md`'s "Spawn the reviewer" branch directly and skips its "Who runs the spec review?" picker; that picker's "My own session" is reached by "Not now" plus the paste prompt. The plain path asks one question and the tracking-issue path two, on purpose: a plain issue's review is the quick check, and the tracking issue's is a stage. Without `AskUserQuestion`, "Not now" is the default and the report says so.
- **R13.** A session that files several plain issues in one go, as `findings-review` step 5 and `closeout.md` step 5 do, asks once for the batch and reviews them as a set. `decomposing.md` step 6 already hands its set over and is unchanged. The batch offer asks one question, and "Spec-review it now" starts one set reviewer per repo, each with `Review <URL>, <URL> as a set.` for that repo's issues; `issue-reviewer` is unchanged. Because: one picker is R12's cost of accepting, and a set review is per repo (https://github.com/dbaggott/claude-plugins/issues/471#issuecomment-6458301298). A flow that asks for its batch makes no per-issue offer (`filing.md`, "Offer the spec review").
- **R14.** `project-status`'s `review-spec` row names the picker, so the prompt to paste and the in-session offer agree.

### Cross-cutting

- **R15.** Every edited reference stays under C6's cap; a file that would pass it is split at a heading in the same PR. Because: the cap, not a file's size before the change, is the bound, so a child's step that said "shrink or hold" is met by a file that grows and stays under it, as `issue-reviewer/references/rounds.md` did for its R4 close-out (https://github.com/dbaggott/claude-plugins/issues/472#issuecomment-6458659697).
- **R16.** `docs/design/planning-and-orchestrating-multi-issue-projects.md` is history and is not edited; this document records what changed. *(end-to-end: A8)*
- **R18.** The README's description of the flows is rewritten once, at the end of the project, by https://github.com/dbaggott/claude-plugins/issues/408 adopted as a child: it documents each stage with its prompt, that GitHub is the state, the spec-review offer, the close-out each role makes, and the `retrospectives` key. No earlier child edits `README.md` beyond what its own change makes false.
- **R17. Forge seam, cross-cutting.** Every child lists it in `Covers`, since each edits skill text. The close-out and handoff sections, the shared report reference, the retrospectives policy and the spec-review offer name no forge command: a read or write they need goes through an existing script's forge-neutral result line, or a new script in `fetch-issue-state.sh`'s shape with its GitHub assumption marked once, per `docs/forge-support.md` and the contract https://github.com/dbaggott/claude-plugins/issues/149 defines. The two stores stay keyed on `<owner>/<repo>` under a root with no host in it, as today, and a child that finds that insufficient for a second host raises it as a finding rather than adding a host segment on its own. `docs/forge-support.md`'s per-skill table gains a row, or changes one, for each skill whose gate this project moves: `process-review` and `findings-review` stay never-gated, and the spec-review offer declines on the host in the issue's URL as `issue-workflow` already does.

## Decisions

- **D1. The trigger for a close-out is the end of a role's work, defined in that role's skill, never the dispatch.** Because: a dispatched agent and a standalone session doing the same role's work produce the same artifacts, and the flows diverged only because the instruction was attached to the dispatch. Revisit if: a role turns up whose standalone and dispatched ends differ in kind rather than in who reads the report.
- **D2. The `retrospectives` key has two states and defaults to `off`.** Because: retrospectives exist to improve the plugin, which is the maintainer's concern, and an average user should not carry files they never asked for; the maintainer sets it on. The alternative, always writing the file and gating only the surfacing, was rejected because it leaves files under `~/.claude` for users who never opted in. Revisit if: users with it off report friction that a batch read would have counted, or a three-state (`on`, `off`, `write-only`) is asked for.
- **D3. Severity, for the off state, is two observable classes, not a judgement.** The classes are two of the retrospective's four headings, whole: every item that would go under **Skill wrong or missing** (an instruction wrong or contradicted by the tree, quoting the line) and every item that would go under **Worked around**. Items under **Slowed or blocked** and **Wished to ask** are not surfaced; a block that stopped the task is already in the report as the outcome, not as friction. Because: an agent's sense of "severe" is noisy, and taking two headings whole means the on and off states classify identically and no heading is split by judgement. Revisit if: the off state's surfacing is still too noisy, or misses the class of problem the maintainer needed to hear about.
- **D4. Findings before the merge, retrospectives after.** Because: a finding can change the PR, so it has to arrive while the operator can still act, and the merge handoff already exists as that moment; process friction changes only the plugin, and the role's end is when it is complete. Revisit if: a class of finding only becomes visible after the merge, such as a post-merge CI failure, which the delta report then carries.
- **D5. Each artifact's format lives with its consumer.** `entry.md` under `findings-review`, `retrospective.md` under `process-review`, the shared report under Q1's answer. Because: the consumer is the one party every producer has in common, and a format under one producer reads as that producer's. Revisit if: a format gains a second consumer that needs a different shape.
- **D6. Both sides write a finding they each own, and the sweep merges.** Because: the flow-inference rule asks the reviewer to know the author's session, which it cannot; a duplicate file costs a merge step that already exists, and a lost reviewer finding costs an issue nobody files. Revisit if: duplicates dominate the sweep.
- **D7. The retrospective prompt, frontmatter and file name are unchanged.** Because: 190 existing files and `process-review`'s grouping depend on them, and nothing in this project needs a different shape. Revisit if: never, within this project.
- **D8. The off state surfaces through the existing always-on rule's path, not a new one.** Because: "tell the user, offer to file upstream with approved text" is already the plugin's contract for shipped tooling that does not fit; this project narrows when it fires, it does not add a channel. Revisit if: the always-on rule's text grows past what every session should pay for, in which case the detail moves to the shared report reference and the rule points at it.
- **D9. The seam is kept by construction, not by a later port.** Because: the plugin's stated direction is a second forge behind the script layer (https://github.com/dbaggott/claude-plugins/issues/21, https://github.com/dbaggott/claude-plugins/issues/149), and prose that names `gh` is the one thing a port cannot adapt; the orchestration project's R28 held the same line and its as-built doc records that it held. Revisit if: issue 149 defines a contract the scripts here do not fit, in which case they move to it.

## Open questions

Each was built at its stated default.

- **Q1. Where does the shared report reference live?** Default: `findings-review/references/report.md`, because the report is where findings entries are born and the file already sits beside `entry.md`; a resolver who finds a neutral home that costs no new skill directory may propose it in the PR. **Settled at the default**: `findings-review/references/report.md` (see R1).
- **Q2. Does the reviewer's handoff turn end in orchestration, or only in a standalone session?** Default: it ends in both. The orchestrator already receives turn ends as events, and one more wake per PR is the price of relaying the reviewer's view before the merge. **Settled at the default**: it ends in both; `orchestrate/SKILL.md`'s "Wait on subagent reports" holds the reviewer's handoff for the relay (R10).
- **Q3. In the off state, does a subagent's surfaced friction reach the operator?** Default: through its report, which the dispatcher relays under Observations; a subagent cannot offer to file (C7), so the offer is the main session's. **Settled at the default**: the subagent puts its `Friction:` lines in its report, the dispatcher relays them under its own Observations, and the offer to file is the main session's (`process-review/references/retrospective.md`, "When a retrospective is written").
- **Q4. Does the batch spec review in R13 run before or after the follow-ups are filed?** Default: after, as one set review on the filed issues, so the review has URLs to post on. **Settled at the default**: after, as one question for the batch and one set review per repo on the filed issues (R13).
